<Note variant="scope" title="A different model from the article">
This page collects the design and experiments of the translation Transformer in *Attention Is All You Need* (Vaswani et al., 2017) that the article leaves out. Unlike the article’s small language model, this translator pairs an encoder that reads the source with a decoder that writes the translation.
</Note>

<Section id="attention" locale="en" doc="paper">

<div id="problem">

Suppose we want to translate this sentence.

> The animal didn't cross the street because **it** was too tired.

What does **it** refer to — the animal, or the street?
The phrase "too tired" settles it: animals get tired, streets do not.
But to make that call you cannot look at **it** alone. You have to look back at *animal*
and forward to *tired* at the same time.

  describe="The full description is in the diagram's alternative text."

>
  <AttentionArcs locale="en" />
</Figure>

A machine has the same job. When it processes one word it has to consult the other words
in the sentence. The question is **how**.

### Reading one word at a time

Until 2017 the standard part for this was the **recurrent neural network**.
The name is heavier than the idea. It reads left to right, carrying one running note
that summarises everything it has seen so far.

Each new word updates that note:

```text
note(step 1) + "The"     →  note(step 2)
note(step 2) + "animal"  →  note(step 3)
note(step 3) + "didn't"  →  note(step 4)
...
```

That feels natural — it is roughly how a person reads. But two things about it are awkward.

### Awkward thing one — everything has to wait its turn

To compute note(4) you need note(3) first, and note(3) needs note(2).
A hundred-word sentence means a hundred steps that **must happen in order**.

This matters because the hardware doing the work, a GPU, is a machine for doing thousands
of things at once. Work that has to queue leaves all that capacity idle.
It is like having a hundred people available and using them one at a time.

<Figure
  caption="The same five tokens. Above, they queue and take five ticks; below, they run together and take one."
  describe="The full description is in the diagram's alternative text."
  wide
>
  <SerialWait locale="en" />
</Figure>

<Note variant="why" title="Doing a lot of arithmetic and having to queue are different problems">
The total **amount** of arithmetic in running one sentence is not especially large.
The problem is that it has to form a queue, and the queue grows with the sentence.
</Note>

### Awkward thing two — distant words stay distant

For information in the first word to reach the last word, it has to survive every note
in between. Each note is rewritten from scratch, so the further it travels the fainter
the original gets.

<Figure
  scrollable
  caption="The same five tokens, connected first one way and then the other."
  describe="The top row connects only neighbours, so reaching token 5 from token 1 takes four steps. The bottom row connects token 1 directly to all the others, so it arrives in one step."
>
  <PathLengthDiagram locale="en" />
</Figure>

The top row is the read-in-order approach: four steps to get from 1 to 5.
For a hundred-word sentence, ninety-nine steps.

The bottom row is the approach this page is about. Token 1 connects **directly** to all
the others. Ten words or a thousand, it is one step.

### So the idea changes

Instead of reading in order: **what if we compute how much every pair of words relates to
every other, all at once?**

Score how much "it" should look at each word in the sentence, then mix information in
exactly those proportions. Nothing waits for anything else, so it all computes
simultaneously — and a word on the far side of the sentence is exactly as close as
the word next door.

That is attention. Everything that follows is about how to turn it into numbers.

<Note variant="limit" title="Attention itself was not new">
The idea of "score how much to look at each thing" already existed and was working well.
It was commonly an attachment **on top of** a recurrent network.
As long as the thing underneath ran in order, the queue was still there.
What changed is that the attachment became the main structure.
</Note>

<Section id="positions" locale="en" doc="paper">

The shared chunks need **positions as well as IDs**. An ID identifies a chunk; it is not its current position.
For a separate order example, compare “the dog bites the man / the man bites the dog”: the word lists match, but the roles differ.
The common I / went / to school chunks occupy positions **0 / 1 / 2**. We add a position vector to each embedding.

### What kind of numbers would do?

These are useful properties considered in this design; they are not requirements that every architecture must meet in this exact way.

1. **They have to differ from position to position**, or they distinguish nothing.
2. **They must not get large.** They are added to an embedding, and a position value
   that overwhelms the embedding buries the meaning of the word.
3. **They have to exist for sentences longer than anything seen in training.**
   Position 500 may never have come up, and something still has to be returned.

Conditions 2 and 3 rule out the obvious idea of using the position number itself.
A value of 100 at position 100 is far too large.

Angles here are in radians: one turn is 2π ≈ 6.283, with π about 3.1416.

### Sine and cosine

The paper chose sine and cosine because they meet all three conditions at once. They stay
between −1 and 1 however far out you go, which settles condition 2, and they return a value
for any position number, which settles condition 3. Condition 1 is met below, by giving each
pair its own speed.

<Expand summary="If sine and cosine are new to you">
Picture a point going round a circle. Its **height** is the sine and its **sideways
position** is the cosine.

Both stay between −1 and 1, and both return to where they started after a full turn.
Bounded values satisfy condition 2. Their formulas can be evaluated at **any position**, including positions outside the training range, which satisfies condition 3. Repetition alone does not explain that ability. Different frequencies help distinguish positions, as shown next.
</Expand>

### Why each pair runs at a different speed

A sine repeats after a full turn. Angles 0 and 2π both give 0; a single wave cannot distinguish repeated periods. This does not say integer positions 0 and 6 have exactly equal values. So a fast-turning pair separates nearby positions, and a
slow-turning pair separates distant ones. A larger divisor makes an angle change more slowly with position, so **each pair turns at its own rate**.

With $d_{\text{model}} = 4$ our example has two pairs.

- Pair 0 ($i = 0$): the denominator is $10000^0 = 1$, so it is just $\sin(pos)$.
  One turn every **6.28 positions**.
- Pair 1 ($i = 1$): the denominator is $10000^{1/2} = 100$, giving $\sin(pos/100)$.
  One turn every **628 positions**.

At position 1, pair one uses 1÷1=1 radian, giving (sin 1, cos 1)≈(0.841, 0.540).
Pair two uses 1÷100=0.01, giving about (0.010, 1.000). Compare positions 0 and 1, then change only the pair to see the slower movement.

<PositionExplorer client:load locale="en" />

<Expand id="math-position" summary="How does sine and cosine produce four numbers at position 1?">

First divide position 1 by 1 and by 100, producing angles 1 and 0.01. Apply sine and cosine to each angle to make four values.

$$
PE_{(pos,\,2i)} = \sin\!\left(\frac{pos}{10000^{2i/d_{\text{model}}}}\right), \qquad
PE_{(pos,\,2i+1)} = \cos\!\left(\frac{pos}{10000^{2i/d_{\text{model}}}}\right)
$$

Map the lab’s inputs and outputs to the formula:

- $pos$ is the token position, counted **from 0** in this formula. This differs from the matrix-cell notation counted from 1 above.
- Value positions and pair indices here also start at 0.
- $i$ counts **pairs** of slots in the vector. Slots 0 and 1 are one pair, slots 2 and 3 the next.
- Even slots take the sine, odd slots the cosine.

Here pos=1 and d_model=4. Pair i=0 gives divisor 1; pair i=1 gives 100. Slots 2i and 2i+1 are the sine and cosine outputs of each pair.

A clock helps. The second hand goes round quickly, the hour hand slowly. The second
hand alone cannot tell a minute from an hour and a minute; together they can.

Same here. The paper’s base model has $d_{\text{model}} = 512$, so 256 pairs — a clock with 256 hands.

</Expand>

### Values computed for each position

Inspect the shared positions 0, 1 and 2 first. Later rows and slider positions 0–11 explore the same rule on a longer input.

  describe="The full description is in the diagram's alternative text."

  wide>
  <PositionRows locale="en" />

Position 0 is exactly $(0, 1, 0, 1)$, because $\sin 0 = 0$ and $\cos 0 = 1$.
Position 1 is $(0.841, 0.540, 0.010, 1.000)$.

Notice how little the right-hand pair moves. One turn takes 628 positions, so by
position 3 it has travelled 0.03. That is the slow hand.

### Added, not multiplied

This vector is **added** to the embedding.

$$
\text{input} = \text{Embedding}(\text{token}) + PE(\text{position})
$$

Not multiplied, and not stuck on the end. Concatenating would make the vector longer
and every later calculation larger; multiplying would leave any embedding slot that
happens to be 0 at 0 regardless of position.

Adding keeps the length and lays the two pieces of information over each other. So that
neither drowns the other, the paper scales the embedding by $\sqrt{d_{\text{model}}}$ to
bring the two to a similar size. Sharing
one slot between two things sounds lossy, but the layers above multiply by $W$ and can
pull out whichever they need.

<Note variant="why" title="Why not just learn them?">
You can. Keep one vector per position and learn those too.

The paper tried both. With learned positional embeddings BLEU was 25.7; with the
sinusoids it was 25.8. **Almost no difference.**

The reason it still chose sinusoids is stated plainly: they **extend to sentences
longer than those seen during training**. A learned table has rows in its allocated range, but none outside that range; unseen allocated rows may be poorly learned. A sinusoidal formula can calculate new positions, which is distinct from guaranteeing good predictions on longer text.
</Note>

</Section>

### Fixed total width keeps computation similar

<Figure
  scrollable
  caption="One head using all 512 slots against eight heads using 64 each. The total width is the same."
  describe="The full description is in the diagram's alternative text."

>
  <HeadBudget locale="en" />
</Figure>

It sounds wrong, but the paper splits the work into eight heads without doing more work.

The trick is that they **share** the width. $d_{\text{model}} = 512$ is divided into
eight parts of 64.

$$
d_k = d_v = \frac{d_{\text{model}}}{h} = \frac{512}{8} = 64
$$

Instead of one head working in 512 dimensions, eight heads work in 64. Since
64 × 8 = 512, the total is about the same — but now there are eight things to watch
instead of one. Not eight times in turn but eight **at once**: the eight $512 \times 64$
$W_Q$ matrices laid side by side are one $512 \times 512$ matrix, so in practice it is one
large product.

| Symbol | Meaning | The paper's model | This example |
| --- | --- | --- | --- |
| $h$ | number of heads | 8 | 2 |
| $d_k = d_v$ | width one head uses | 64 | 2 |
| $h \cdot d_v$ | width once joined | 512 | 4 |
| $W^O$ | the last weight matrix | $512 \times 512$ | $4 \times 4$ |

<Note variant="why" title="Do the heads actually help?">
The paper compared head counts while keeping total width 512 and changing per-head width with them: $h = 1$ drops BLEU to 24.9. BLEU is a translation-quality score: higher is better,
and how it is measured is in the last section. The default of $h = 8$ scores 25.8.

More is not simply better, though. At $h = 32$ it falls back to 25.4. Splitting too
finely leaves each head with a $d_k$ of 16, which is not much to work with.
</Note>

<Note variant="limit" title="Nobody assigns the heads their jobs">
There is no instruction anywhere saying "head 1 finds the subject, head 2 watches
tense". It is all learned, and there is no guarantee the result is anything a person
would have a name for. Different initial weights and learned projections can produce different patterns. Some heads can still be redundant; the architecture alone does not guarantee distinct roles.

The paper is careful about this too. Of the figures in the appendix it says only that
heads **appear** to exhibit such behaviour; it does not claim that attention weights
explain what the model decided.
</Note>

</Section>

### Compare the paper’s translation architecture

Now use a **separate conceptual translation example**: five English source chunks, each represented by 512 values. IDs and probabilities are illustrative; block counts and width describe the paper’s base setup.

The structure has two parts.
The **encoder** reads the input sentence and produces a representation of it;
the **decoder** consults that representation while producing the output one word at a time.

<div id="paper-translation">

### 1. Turn the sentence into numbers

This revisits tokens → IDs → embeddings. The illustrative five-token sentence gives five rows.
The original model has 512 features per row; hand calculations use three tokens with four features. These are different example sizes, not the same computed word meanings.
Revisit <a href={docHref('en', '') + '#tokens'}>tokens and vectors</a> if the input representation is unclear.

### 2. Telling it the order

The [position unit](#positions) showed why handling tokens together still requires order information. Check that reason in the whole route:

> The dog bit the man / The man bit the dog

Both sentences contain the same tokens. Without order information they cannot be told apart.

Before adding the order, the five rows are stacked on top of each other. We decided to handle this source sentence’s five tokens **at once**, so the five rows have to travel as one
bundle. Five rows of 512 cells form a **matrix**. This is a table of values; a model block is a set of operations. (frame 3)

Then a different row of 512 numbers is generated for each position and **added**, cell by
cell, to the row in that position: the first position's row to the first row, the second to
the second. That is the ⊕ in the diagram. It is added rather than stuck on the end so the
row stays 512 cells long. After adding, the matrix is still five rows of 512. What numbers
fill the position row is worked out in the positions section. (frame 4)

### 3. The encoder reads, six times over

Right now each row holds **only its own word and its own position**. But a word's meaning
depends on its neighbours: what "it" refers to can only be settled by looking at "animal".
So every row has to look at the other rows and take what it needs. That is the encoder's job.

That matrix, five rows tall, now enters the encoder, which is **six layers of the same structure**
stacked. “Same structure” means the same shape and order; the numbers inside differ from layer
to layer. Each layer has two parts, passed through **in order**:

1. **attention** — every row looks at every other row in the matrix and mixes in what it needs to settle its own meaning
2. **feed forward** — each row sorts through what it gathered, separately per row

The paper’s base model chooses six blocks of this structure. Each learns its own coefficients; one block’s output becomes the next block’s input.

Six layers later, five rows come out. The count and the shape are unchanged.
What changed is the values: each row now **carries the context of the whole sentence**. (frame 5)

### 4. The decoder writes, one word at a time

The decoder also stacks six layers, but each has **three** parts rather than two.
What goes in is the output words produced so far (the words step 5 chose in earlier rounds), turned into rows and given positions the
same way the input was. At the very start nothing has been produced, so only a **start
mark** goes in, and that one row makes the first word.

1. **masked attention** — the output words produced so far mix among themselves
2. **attention over the encoder** — where the source sentence enters the output side. For every word it writes, the decoder re-reads the encoder's five rows, that is, the whole source. The asking side is the decoder's rows and the answering side is the encoder's five, so the two counts need not match. This is where translating happens
3. **feed forward** — as in the encoder

"Masked" means this: the decoder is the half producing text, so while making the third word
it must not see the fourth — that word does not exist yet. The device that blocks the view
forward is called the **mask**, which you switched in the earlier <a href={docHref('en', '') + '#positions'}>mask unit</a>. (frame 6)

  <CrossShape locale="en" />

### 5. Make the next word’s probabilities

To pick one next word, every entry in the vocabulary needs a comparable score. So the
row at the position being written, one row and not one per row, is taken from the decoder's
last layer and turned into one number per vocabulary
entry, and those become probabilities that sum to 1 — the probability that the next word is
each candidate. The highest candidate is the next word; it is appended to the output and we
go back to step 4, until the end mark comes out. Taking the top one is not always best; the
generation section compares the choices. The earlier softmax calculation makes these numbers sum to 1. (frame 7)

<Note variant="limit" title="Probabilities show up in two places">
**The probabilities inside attention** say how much this word draws from each position in the
sentence. There are as many as there are tokens — three, in the example coming up. They are
not an output but a value inside the calculation, one such row per row.

**The probabilities at the top** say which word comes next. There are as many as there are
vocabulary entries, typically tens of thousands.

Same calculation, entirely different things being scored.
</Note>

### The sizes

These keep coming back. Values are for the original base model.

| Symbol | Meaning | Value |
| --- | --- | --- |
| $n$ | tokens in the sentence, i.e. rows in the matrix | varies |
| $d_{\text{model}}$ | numbers representing one token, i.e. cells in a row | 512 |
| $N$ | layers in the encoder and in the decoder | 6 |
| $h$ | how many separate views attention runs (the *heads* you computed) | 8 |
| $d_k$, $d_v$ | numbers one view works with | 64 each |

These are not learned but **chosen** by the designers; why $64 = 512 \div 8$ is worked out
in the heads section.

<Note variant="scope" title="Learning and using are different passes">
The decoder input at the bottom of the diagram reads "Outputs (shifted right)". Shifted right
means a start marker is put in front of the correct sentence, so that the input at each
position is the correct answer up to just before that position.

**While learning**, the targets are known. Prepare the shifted input and each position’s target, then compute the positions together. The mask is what stops it copying the answer.

So while learning, probabilities are taken from **every row** and each position is scored;
while using it, only from the row being written.

**While actually translating**, there is no correct sentence. The model makes the first
word from the start mark alone, appends it to its own input, produces the second, and so on.

So: **all at once while learning, one at a time while using.**
</Note>

**While learning**, shift the answer one position to the right. Pair input `start / I / went / to school` with targets `I / went / to school / end`: every position predicts the next token.
The **causal mask** hides later inputs, including the token that position is trying to predict. Shifting the input and masking future positions together allow simultaneous computation without copying the answer.

**While using it**, there is no answer. Making the third word needs the second, and
making the second needs the first. There is no way around going in order.

So how is the first one made? Nothing has been written yet, so the decoder is given only a
**start mark**. That single row reads the source in the attention over the encoder and
produces the probabilities for the first word. The word that comes out is appended after
the start mark, the same decoder runs again, and it stops when the **end mark** comes out.
The start and end marks are not words with a meaning but special tokens slipped into the
vocabulary; each takes a slot there and draws its own row from the embedding table like any
other. The source does not change, so the encoder runs **once**, at the start, and every
step the decoder reads that same result; what runs again and again is the decoder.

<Section id="training" locale="en" doc="paper">

<div id="paper-smoothing">

### Teaching it not to be too sure

The paper adds one thing here. Rather than “1 on went and 0 elsewhere”, it takes a little
of that certainty away.

$$
\text{the answer} = (0.025,\; 0.925,\; 0.025,\; 0.025)
$$

$\varepsilon_{ls} = 0.1$ has been removed and shared evenly across **all four** words, 0.025
each. The right word is one of the four, so it gets 0.025 back: $0.9 + 0.025 = 0.925$. This
is **label smoothing**.

Scoring the default prediction against the two target distributions gives 0.511 and 0.628. This compares **different scoring targets**; other predictions can have a lower smoothed loss. The paper’s report of worse perplexity and better BLEU after training is a separate experimental observation, not a proof from this one prediction.

The paper reports improved BLEU under its experimental conditions. This small probability example alone does not establish an improvement in translation quality for every model.

<Note variant="why" title="What the paper measured">
Turning label smoothing off ($\varepsilon_{ls} = 0$) drops BLEU from 25.8 to 25.3.
Turning it up to 0.2 gives 25.7, also slightly down. 0.1 sits between them.
</Note>

</div>

### The learning rate does not stay put

At the start the weights are meaningless random numbers, and a large step from there
lands somewhere arbitrary and far away. So training starts slowly, moves boldly once things
have settled, and shortens the stride again towards the end so it does not overshoot a
good spot. That is why the paper's learning rate is not a fixed number but changes as
training goes on.

<p data-training-step>One training step computes the loss for one batch of sentences and updates the weights once.</p>

<Figure

  describe="The full description is in the diagram's alternative text."
  wide
>
  <LearningRateCurve locale="en" />
</Figure>

<Expand id="math-schedule" summary="How does the learning rate rise to step 4000 and then fall?">

At the base settings, step 1000 gives about 0.000175, step 4000 about 0.000699, and step 16000 about 0.000349. First compare these points on the curve. The formula chooses the smaller of an increasing and a decreasing rule.

$$
lrate = d_{\text{model}}^{-0.5} \cdot \min\left(step^{-0.5},\; step \cdot warmup^{-1.5}\right)
$$

Whichever of the two terms inside the $\min$ is smaller wins.

- Early on the right-hand one, $step \cdot warmup^{-1.5}$, is smaller, so the rate
  **climbs** in proportion to the step.
- Past 4000 steps the left-hand one, $step^{-0.5}$, takes over and the rate **falls**
  as one over the square root of the step.

The highest point is at exactly 4000 steps, about $7.0 \times 10^{-4}$.

</Expand>

<div id="paper-training">

### How it was actually trained

The conditions the paper records. When the last section compares this model as "better
and cheaper", the cost figures come from the hardware and hours listed here.

Two words in the table first. The model does not correct itself after every sentence; many
sentences are bundled, their loss measured together, and $W$ corrected once. The bundle is a
**batch**, and processing one batch and correcting $W$ once is one **step**, the $step$ in
the learning-rate formula. The sentence pairs are not the model's own: they are text people
had already translated (parliamentary proceedings, news), paired sentence by sentence, in the
standard sets released each year by the **WMT** translation competition, which is what lets
papers compare on equal terms. The newstest sets later are that competition's test sets.

| | |
| --- | --- |
| Data (En→De) | 4.5M sentence pairs, vocabulary 37 000 |
| Data (En→Fr) | 36M sentences, vocabulary 32 000 |
| One batch | about 25 000 source and target tokens each |
| Hardware | 8 P100 GPUs |
| Base model | 0.4 s per step × 100K steps ≈ 12 hours |
| Big model | 1.0 s per step × 300K steps ≈ 3.5 days |
| Adam (the update rule; it sets a separate step size per weight from its recent gradients; not covered here) | $\beta_1 = 0.9$, $\beta_2 = 0.98$, $\varepsilon = 10^{-9}$ |
| Warm-up | 4000 steps |
| Dropout | 0.1 (10% of the values zeroed at random) |

Training loss can fluctuate between batches. Stopping can depend on validation trends and a chosen budget; the paper reports 100K base-model steps and 300K big-model steps. Once trained, weights are frozen and dropout is switched off. Deterministic decoding repeats its choice under the same conditions; sampling can differ with unchanged weights.

<Note variant="limit" title="Dropout is not covered here">
A model that starts leaning on a few routes through itself memorises the training data
and weakens on new sentences. To prevent that, dropout randomly sets some values to zero
during training, so no route can be relied on.

The paper measured it: turning dropout off drops BLEU from 25.8 to 24.6. That is a
large difference for something this article only names in passing.
</Note>

### What BLEU is

Nobody can read and grade thousands of translated sentences by hand, and papers need one
number they can compare. BLEU is that number. It compares the machine's sentence with a
human one and counts **how much of it overlaps**, on a scale from 0 to 100 where higher is
better.

It is not a perfect measure. A correct translation using different words scores low, and
an awkward one reusing the right words can score high. But for comparing models under
the same conditions it is serviceable, which is why it is used. So 100 is not the target to
read it against: a human translation also loses points wherever its word choice differs
from the reference. It can receive a lower score despite being a good translation. What matters is the gap between models scored
on the same data. The significance of a gap depends on the dataset, evaluation procedure and repeated-run variation.

### Score and cost together

Table 2 of the paper does not report scores alone. It puts the **training cost**
alongside them, because that is the argument being made.

<BleuCostExplorer client:load locale="en" />

On English to German, Transformer (big) leads at **28.4**. The previous best was 26.36,
from an ensemble of several models, so this is more than 2 ahead. An ensemble runs several
separately trained models at once and averages their next-word probabilities; it gains a
little and costs that many times more to train and to run. The point is that one
Transformer beat it.

The base model is the more striking row. At **27.3** it passes every previously published
single model and ensemble, with an estimated training cost of $3.3 \times 10^{18}$. Compared with the two ensembles with reported costs in Table 2, this is about **23–55 times lower**: divide $7.7 \times 10^{19}$ and $1.8 \times 10^{20}$ by the base-model cost.

<Note variant="limit" title="The horizontal axis is an estimate, not a measurement">
A FLOP is one addition or multiplication; $3.3 \times 10^{18}$ means about that many
arithmetic operations over the whole of training. The authors did not measure FLOPs. A
footnote says they computed **training time × number
of GPUs × an assumed sustained rate per GPU**, listing those assumed rates as 2.8, 3.7,
6.0 and 9.5 TFLOPS for the K80, K40, M40 and P100. TFLOPS is not a total but a speed, how
many trillion operations one GPU does per second, so the total is speed × time × GPUs.

Good enough to compare orders of magnitude between models; not a precise figure.
</Note>

<Note variant="limit" title="Where the paper disagrees with itself">
The English-to-French score appears twice, differently.

The abstract and Table 2 give Transformer (big) as **41.8**. The body of §6.1 describes
the same model as achieving "a BLEU score of **41.0**".

It was never corrected, not even in the v7 revision posted in 2023. This article quotes

### Which parts actually mattered

With this many parts, the results alone cannot say which part earned the score. Change
one thing and hold the rest fixed, and the difference in BLEU can be credited to that one
thing. So the paper retrained the base model changing one thing at a time. That is Table 3.

| What changed | BLEU | vs base |
| --- | --- | --- |
| (the base setting) | 25.8 | — |
| one head | 24.9 | −0.9 |
| 32 heads | 25.4 | −0.4 |
| $d_k$ of 16 | 25.1 | −0.7 |
| 2 layers | 23.7 | −2.1 |
| 8 layers | 25.5 | −0.3 |
| $d_{ff}$ of 4096 | 26.2 | +0.4 |
| dropout off | 24.6 | −1.2 |
| label smoothing off | 25.3 | −0.5 |
| learned positions | 25.7 | −0.1 |

Some things fall out of that.

- **Depth matters most.** Going from six layers to two costs 2.1.
- **Head count affects this experiment.** One head and 32 heads scored below the eight-head base model. At a fixed total width, more heads reduce the coordinates per head, but this table does not establish that as the sole cause or that eight is always best.
- **Dropout matters more than you might expect.** Turning it off costs 1.2.
- **Sinusoids or learned positions make almost no difference.** 0.1 apart.

<Note variant="limit" title="These numbers are not comparable with Table 2">
Table 3 reports BLEU on the **development** set (newstest2013); Table 2 reports it on the
**test** set (newstest2014).

The checkpoint conditions also differ. Table 2 averages the last **five checkpoints** for the base model and 20 for the big model. Table 3 uses **no checkpoint averaging** (sections 6.1 and 6.2). The 25.8 and 27.3 scores therefore cannot be explained by the dataset alone or treated as an improvement between these tables.
</Note>

### And on something other than translation

To show this was not a translation-only architecture, the paper tried one more task:
working out the **grammatical structure** of English sentences: the tree that groups a
sentence into phrases ("this chunk is a noun phrase, that one a verb phrase"). Written with
brackets, that tree is a single line like `(S (NP the cat) (VP sat))`, which makes
"English sentence → bracketed line" the same kind of job as translation.

A small four-layer model, trained on about 40 000 sentences — not much data. It scored
an F1 of **91.3** (F1 combines precision and recall into one score, 100 being perfect), in line with models built specifically for that task over many years.
Given more data it reached **92.7**.

The point is that an architecture designed for translation was carried over almost
unchanged and did this well.

### The limits the paper names itself

The closing section lists what the authors wanted to do next, which read backwards is
what they had not done.

- **Long inputs.** As the end of the attention section noted, the score matrix is $n \times n$, so cost climbs quickly as sentences grow.
  The paper names restricted attention as a direction.
- **Things other than text.** Images, audio and video are listed as plans.
- **Generation being sequential.** Making it less so is set out as a goal.

These are research directions proposed in the paper at the time, rather than a complete list of improvements in current models.

<Note variant="scope" title="That is the paper">
The starting question was how context produces a next-token prediction.

From there we went through vectors and matrix products, the dot product and softmax,
computed attention, combined heads and positions into one block, updated one coefficient, and chose chunks to extend a sentence.

What remains beyond this guide: full Transformer backpropagation, detailed dropout arithmetic, the full BLEU definition, and every change in modern models. One-weight updates and the basic GPT connection were worked through here.

### Interpret the table yourself

Set the experiment to **English→German**. The base model’s 27.3 exceeds the earlier results and its estimated training cost is lower.
Then switch to **English→French**. The base model’s 38.1 does not exceed every earlier score.
Read data and conditions before reducing a model name to a single conclusion.

| Item | Question to ask |
| --- | --- |
| Dataset and language pair | Is this the same task and evaluation data? |
| Measured quantity | Training cost or the cost of generating a token? |
| Metric | Does BLEU measure translation overlap or factual accuracy? |
| Changed settings | Did coupled values such as head count and head width change together? |
| Scope of conclusion | An experimental observation or a guaranteed property of a calculation? |

Data used to select settings or stopping points has already influenced model selection. Separate test data checks results after that selection.
The difference between 25.8 and 27.3 on different datasets is therefore not an improvement attributable to the model. Repeated-run variation matters too.

### Length costs and limits of the worked example

Dense attention’s score table has n × n cells for n tokens. Predict the cell count before doubling 3 tokens to 6.

| Tokens n | Score cells n² | Relative to 3 tokens |
| --- | --- | --- |
| 3 | 9 | 1× |
| 6 | 36 | 4× |
| 12 | 144 | 16× |

<Expand id="math-cost" summary="Why does doubling tokens quadruple the score cells?">

Three query rows paired with three key rows make 3×3=9 cells. Six of each make 6×6=36 cells.
6 is twice 3, but 36÷9=4. Both rows and columns doubled: 2×2=4. n names the token count; n² abbreviates n×n.

</Expand>

This computes **score-table size**. Total model cost also includes projections, FFN, block count and implementation choices.
Small hand arithmetic does not verify a trained model’s language understanding or hardware speed.
